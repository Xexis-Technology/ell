- **2026-10-05 admin booking detail (owner rejected the tabbed version):** lesson — do NOT hide admin operational content behind tabs. The owner called the Details/Actions/History tab view "no layout design, no proper show". Admin detail pages are now single-document, all content visible, 2-column workspace (main data left, tools aside). Related lesson: a `<p class="label">` placed as a direct child of a CSS grid becomes a grid cell — never mix bare labels into a layout grid; use real section headings.
- **CSS gotcha (admin):** grid/flex children default to `min-width:auto`, so a wide `<table>` inside a card silently stretches the whole page. Any admin grid must use `minmax(0,1fr)` tracks plus `min-width:0` on children; verify with `scrollWidth > clientWidth` checks, not by eyeballing screenshots.
- **Verification gotcha (this machine):** Chrome headless has a ~496px minimum window width, so `--window-size=430` produces a 496px layout captured into a 430px image and looks falsely broken. To test true narrow viewports, load the page in a fixed-width same-origin `<iframe>` (360/390/430px) and measure/assert from inside it.
- **Verification gotcha (auth):** injecting a session cookie into Chrome's `Default\Network\Cookies` does not work here — Chrome purges plaintext and even DPAPI-encrypted rows. Reliable method: a temporary throwaway PHP file that calls `login_user('admin', $u)` then redirects; Chrome stores the cookie itself. Delete the file afterwards.
- **2026-10-05 dispatch board (frontend-design):** the admin dispatch page is a **run sheet**, not a table — ordered by departure time with a time rail and real idle-gap markers ("2 h 45 m clear"). Reason: a chauffeur board's organising axis is time, and "how much slack is left" is the question the page exists to answer.
- **Two-accent rule for admin operations:** brand champagne (`#D9B978`) = the promise (public site, primary action button). New amber `#E8A33D` = the working instrument (departure times, "needs a driver", today's live state). Sodium-vapour amber is what a night dispatch board looks like, and it keeps operational state from competing with brand actions. Never use amber as the only signal — pair it with text.
- **Encoding rule (learned the hard way):** never put literal non-ASCII punctuation (·, →, —, ') in PHP source written via tooling on this machine — an edit round-trip can write `Â·` / `â€²` into the file and it renders as garbage. Use HTML entities (`&middot;`, `&rarr;`, `&mdash;`, `&#39;`). When a page shows `Â§`-style junk, check the *source file bytes* first, then the HTTP `Content-Type`, then suspect your own reading of the screenshot.
- **Validation rule:** a regex is not a date check. `preg_match('/^\d{4}-\d{2}-\d{2}$/')` accepts `2026-13-45` and then `strtotime()` returns false, which fatals downstream. Use `DateTime::createFromFormat` and verify it round-trips (`$d->format('Y-m-d') === $input`). Apply this to every `?day=` / `?from=` / `?to=` parameter.
- **Replacing a native `<select>` changes the POST contract.** An empty `<option value="">` posted `''`, but a JS picker posts `0` for "nothing selected". `$_POST['x'] !== '' ? (int)$_POST['x'] : null` turns that into `int 0`, which passes the falsy availability checks and then dies on the foreign key. Always normalise with a helper that maps `''`, `'0'` and `0` to `null`, and test the clear path as carefully as the set path.
- **Absolute popovers and `100vw` math:** a `position:absolute` box anchored to a trigger at a variable indent cannot be sized safely in viewport units — it will push the page into horizontal scroll at some widths and not others. Fix by changing *mode* with the layout instead of by arithmetic: below the point where the form goes single-column, render the panel inline (static, grows the form); above it, float it and anchor the right-hand one to the trigger's right edge. Keep the float/inline breakpoint identical to the form's column breakpoint.
- **Popover payload:** ship shared JSON once as `<script type="application/json">` with `JSON_HEX_TAG|JSON_HEX_AMP|JSON_HEX_APOS|JSON_HEX_QUOT`, then `JSON.parse(...).textContent`. Never inline JSON into `x-data="{...}"` — this codebase already got burned by that once (see the blank-form fix).
- **2026-10-05 client book (frontend-design):** the admin now has ONE instrument language across pages — mono for anything that identifies or dates, amber for "needs a person or a decision", green for settled, champagne serif reserved for the client's name and money. The client book is the ledger facet of that same system, not a separate theme. The deliberate risk: **lifetime billed is the largest type on the page**, because a limo company lives on repeat clients, so the relationship's value is the real headline. Most admin pages lead with a row count.
- **Use container queries for anything inside a multi-column admin layout.** A viewport media query cannot know how wide a panel actually is: at a 1080px window the two-column customer split leaves the sheet ~440px, where five fixed table columns collapse the flexible one to 0px and overflow the card — while the same viewport at a single-column breakpoint looks perfect. `container-type: inline-size` + `@container name (min-width: …)` is the correct tool.
- **`COUNT(*)` over a LEFT JOIN counts rows, not entities.** `SELECT COUNT(*) FROM customers c LEFT JOIN bookings b ...` reports a client with 7 rides as 7 clients. Use `COUNT(DISTINCT c.id)`. Always assert a header count against a direct `SELECT COUNT(*) FROM customers` before calling a page done.
- **2026-10-05 fleet & crew (frontend-design):** the two Fleet pages are **dockets**, not tables, sharing one `fl-*` component set. The signature is the compliance clock: bar length = time remaining against a 12-month horizon, colour = urgency. Length and colour are deliberately **two independent channels** — an early version encoded both in length and made a lapsed document draw the longest bar, which read backwards.
- **Schema is not the product.** `vehicles.insurance_expiry / registration_expiry / inspection_expiry / diamond_sticker_expiry` and `drivers.license_expiry / reference / license_number / payout_reference` had existed in `database.sql` for weeks with no form writing them, so every value was permanently NULL. When redesigning a page, diff the table's columns against the form's inputs — the gap is usually the actual bug.
- **Iterate by index (`foreach ($rows as $i => $r) { $rows[$i][...] = ...; }`), not by reference, when enriching rows.** The by-reference form needs a matching `unset($v)` or every later loop silently aliases the last row; the index form has no footgun and reads the same. The actual fleet-docket bug was worse: the enrichment loop looked the four dates up through a `$WATCH` key=>label map **by label** instead of by column, so every lookup missed, all six cars counted as missing dates, and the filters collapsed to a single bucket. When a derived figure is uniformly wrong, dump the raw value and the computed value from the same loop before touching the math.
- **One SQL list cannot serve both UPDATE and INSERT.** `SET col=?` is valid for UPDATE but `col=?` is a syntax error in an INSERT column list. Build a bare column list and derive the `SET` form from it.
- **`flash()` decides read-vs-write on `func_num_args()`, so `flash('key', '')` WRITES an empty value instead of reading.** It looks like a guarded getter and silently eats your message on every page load. The admin panel's actual PRG convention is a `?ok=` / `?err=` query parameter; use that and do not reach for `flash()` here.
- **Editing a heading means editing its parts, not its markup.** The public heroes carry inline structure (`<br>` for the line break, `<em>` for the champagne accent). Exposing such a heading as one text field lets a comma delete a design decision. Split it into `_lead` / `_accent` / `_tail` and keep the tags in the template. Same principle put every button destination behind a closed `<select>` of internal routes: there is no way to type `javascript:` if the field cannot hold anything else.
- **Restoring an "absent" value needs DELETE, not UPDATE to NULL.** Revisions store NULL to mean "this field had no stored row, it was showing its default". Restoring by UPDATE writes NULL and renders an empty string. When the old value is NULL, delete the row so the default comes back.
- **A failed upload must resolve against the previous value, and a "leave alone" control must resolve against the field default.** Resolving an unchanged control with no default stores `''`, which blanks the control until the next save. Label such options by what they actually do ("revert to the default"), not by what the author hoped they would do.
- **2026-10-13 User Page Design Manager (frontend-design):** `app/PageContent.php` holds the field registry for the 8 public marketing pages; `admin/user-page-design.php` edits it. The registry is the single source of truth for both the editor and the fallback, so a missing DB row renders the page's original copy rather than a blank. Built-ins that matter: `LINKS` (closed destination allowlist), `IMAGE_RULES`, and the paired `<key>` / `<key>_alt` image fields. Verify with: no page overflow, a refused upload leaves the previous image intact, and the `<br>`/`<em>` classes still present in the rendered `<h1>`.
- **A field list cannot express "add one" or "move this up".** The FAQ questions on `legal/faq.php` were the first content on this site that is genuinely *rows*: the desk adds, reorders, hides and deletes them. Those need their own tables and their own POST operations - a registry field can only be edited, never created or removed. Split it: fixed copy stays in `PageContent::PAGES`, the row set goes in `faq_groups`/`faqs`, and the editor drives both from one endpoint (`op=save` for edits so it rides the existing autosave; explicit ops for add/move/delete).
- **Order-by direction must be the OPPOSITE of the comparison when finding a neighbour.** "Move this row up" needs the nearest row *above* it, which is `sort_order < mine ORDER BY sort_order DESC`. Writing the same direction for both picks the furthest row instead, so the move appears to do nothing. The swap itself then has to read both values before writing either - writing one value to both rows is the same bug wearing a different hat.
- **Never inline `json_encode()` into an HTML attribute.** `x-data="{cat:<?= json_encode($x) ?>}"` emits double quotes that close the attribute early; Alpine never initialises and every `@click` throws `cat is not defined`. Use `e(json_encode($x, JSON_HEX_APOS|JSON_HEX_QUOT))`.
- **A field default and a field value are not the same shape.** Link fields default to a *label* ("Contact us") and store a *path* ("legal/contact.php"). `page_content()` returns the default verbatim, so a public page that uses it directly renders `href="Contact us"`. Every render site must resolve with `PageContent::safe_link()` first - the other seven pages already did, which is why the FAQ page was the only one to break.
- **A fallback list is not the same as a seed list.** The 14 original FAQ questions stay in `legal/faq.php` and are used whenever the table is empty, so "nobody has edited it yet" and "someone deleted them all" both render the page you already had instead of a blank section.
- **A guard clause that can never fire is worse than no guard.** "Reject a bad link" was written `if ($safe === '' && $raw !== '')`, but the resolver returns the *default* rather than empty, so the branch was dead and bad input was silently replaced with the default. Validate the input against the allowlist directly; never infer validity from the resolved value.
- **`â†` on a page is double-encoded UTF-8, not a broken character.** It is the original `→` (U+2192, bytes `E2 86 92`) after being decoded as Windows-1252 and re-saved as UTF-8: `E2`->`â`, `86`->`†`, `92`->`’`. The same pass also turned `·` into `Â·`, `—` into `â€"`, `✕` into `â€•` and `✓` into `â€œ`. **The file is then MIXED** - some runs damaged, others still perfect - so `mb_convert_encoding` over the whole file "fixes" the first group and shreds the second (63 runs became 200+ broken characters). The only safe discriminator is byte-level: map each character back to the single Windows-1252 byte it came from, then walk those bytes as UTF-8. A well-formed multi-byte sequence means the run really was double-encoded; a lone `0x97` (a correct em dash) is not valid UTF-8 and can never be collapsed by mistake. Note `mb_convert_encoding($s,'Windows-1252','UTF-8')` is the call that produces the recovered bytes, not the reverse.
- **A filter's option set is not the same as its data's taxonomy.** The location picker has two chips (Airports / Everything else) but the data has five types. Handing the raw type to the filter made rail, bus and cruise locations disappear the moment "Everything else" was switched on. A display label and a filter value are allowed to differ; a filter value must be coarser than the data, or narrower.
- **When a list moves from a hardcoded literal to the database, prove the new list equals the old one.** Locations shipped as two identical literals that drifted; moving them to a table without diffing the output against both originals would have quietly changed what riders see. Compare row by row, not just by count.
- **A POST-redirect form is a page state, so a tab over it must be a URL.** Adding a second tab to `admin/settings.php` looked like a two-line change and was not: every form there redirects to the page, so a tab held in `localStorage` or a JS toggle would dump the admin back on the default tab after every save, and the bar would be dead without JS. Render `?tab=` server-side against a closed `in_array` allowlist and let it be two real links. The allowlist is also the XSS guard - `?tab=` is echoed back, so a value like `locations" onmouseover="` is a live injection attempt, and the allowlist rejects it. **And when you introduce a tab, re-audit every redirect that page already had:** they all pointed at the old single-page URL, and the ones for the new tab's forms would have landed on the wrong tab with an anchor to an element no longer in the DOM.
- **A grid row with auto-placed children fails at the width you did not test.** The location row was `grid-template-columns:auto minmax(0,1fr) auto auto` holding five children, so `.st-loc-tools` silently took column 1 on the second line and stretched it from 24px to 98px; the type select's `min-width` and a `nowrap` label took the rest and the name input got **0px**. Nothing errors, no overflow is reported, and it looks fine on desktop - `minmax(0,1fr)` is specifically built to shrink to nothing rather than overflow. **Assign `grid-area` to every child on the narrow layout**, not just the container's template, and assert the measured width of the field that matters (`main=230 name=230`) instead of trusting a screenshot.
- **Put the primary action above a long list, not under it.** "Add a location" sat after eighteen rows, so the first thing an admin wanted was the last thing on the page. The test is whether the primary action is reachable without scrolling - a form that adds to a list belongs above that list at every width, not only the one that complained.
- **ANDing a filter with a search box hides matches the user can see.** The location picker's Road/Airport chips were ANDed with the query, so tapping Road and typing "Kennedy" returned "No matches" - for JFK, the first row of the list. The rider was then pushed to the free-text fallback and lost the saved location, its area and its type. The rule: **the query is checked first; a filter only applies when the box is empty.** A filter narrows what you are *browsing*, it is never a gate on what you typed - a control that hides a literal match for the user's own words is always wrong. Corollary: while a filter is not being applied, it must say so (dim it, title it), because a highlighted chip that does nothing is a lie in the UI.
- **A picker exists in two implementations; a fix in one is invisible in the other.** `index.php` carries its own inline Alpine component and `assets/js/booking.js` carries a shared one, both with their own `filteredLocs()`. They were byte-identical, which is exactly why the bug was in both. Any change to picker behaviour has to be made and asserted in both, or the two pages quietly diverge.
- **A filter list must not be a subset of the data's own categories.** Settings listed five location kinds (airport/rail/bus/cruise/place) while the rider's picker chips were hardcoded as two (Road/Airport), so three of the five categories were unreachable from the filter and `locations_json()` had to collapse `kind` into airport/road to hide the mismatch. **Render filter controls from the data** (`counts` walked out of the payload, then a fixed display order) so a new category shows up the moment a row of that type is added, and a category with no rows gets no dead chip. A collapse like that is a bug waiting for a user to notice the two screens disagree.
- **Two hardcoded chip blocks are two places to forget.** The chips for the location picker lived as literal buttons in `index.php` *and* `services/booking.php` while the data came from `assets/js/booking.js`. Any change to filtering had to land in all three, and the leftover `t: 'road'` in the JS fallback is the kind of thing that survives a search for the visible bug. When a control moves to data-driven markup, grep for the literal it replaced and for the fallback values too.
- **"Every page" means put it in the shared layout, not a flag per page.** The first version of the openIntelix credit line needed a `$showCredits` flag on six service pages, because it was scoped to them. Asked for it on every page, the whole thing collapsed to one unconditional `require_once` of `views/partials/credits.php` inside `views/layouts/public.php`. If a per-page opt-in becomes a universal requirement, the flag was the wrong shape.
- **A square-hosted logo is a white block waiting to happen, and sometimes the answer is to drop it.** The openIntelix image was a 400x400 PNG with a white background: on a near-black page it rendered as a large white block, and clipping it to the mark took two attempts and a pile of CSS. When the owner asked for text only, the honest fix was to delete the image, the request and the rules - not to keep tuning the crop. If an asset fights the design twice, ask whether it earns its place.
- **A per-stage re-sort can silently undo the ORDER BY you already wrote.** Group events fetched `created_at DESC` from SQL, then a `usort` compared ages descending and put the *oldest* inquiry at the top of its stage - the SQL order was undone in PHP. When a second sort runs after the query, it owns the ordering entirely: re-state the intent (`$a[age] <=> $b[age]` for newest-first) and add an `id` tiebreak, because two rows from the same day otherwise swap places between renders.
- **A badge must count something actionable, not how many rows a table has.** The sidebar badges use the same queries as `admin/dashboard.php` - awaiting pricing, pending drivers, requested payouts - precisely so the badge and the dashboard cannot disagree. Nine of eighteen links deliberately show nothing: a "312" on Customers or "1,404" on Reports is not information, and one un-actionable badge teaches an admin to ignore all of them. Also: `information_schema` queries in this project return rows for several tables at once, so a `COLUMN_NAME LIKE ...` probe will happily report `notifications.title` when only `blog_posts` has one. Ask for `TABLE_NAME` too, or read the column list off the page that already queries the table.
- **"Latest first" is not a rule you apply to every ORDER BY.** Auditing all eighteen admin pages, four lists genuinely needed newest-first (customers, payouts queue, payout lines, passkeys) and eleven were already correct - but drivers by name, vehicles by make/model, dispatch by trip time, coupons by code, vehicle categories, reports by date and every hand-positioned `sort_order` list are ordered **for lookup**. Flipping a roster to recency breaks the only thing it is for: finding the name you half-remember. Sort by what the list is *for*; recency is only right where a row can be *missed*.
- **A badge should not count the page you are on.** `$navActive === $f` suppresses it there: the item is already on screen, so the number is noise, and it returns as soon as you navigate away. Keep the count fetched - only the current page's render drops it.
- **A restore script that reports failure is worth reading twice.** A cleanup step silently matched zero rows because it passed an email into a `WHERE id = ?`; MySQL coerced the string to 0 and updated nothing. Nothing was corrupted, but a `var_export($h === $orig, true)` line printed `false` and got treated as noise. When a verification line prints false, stop and find out which of the two sides is wrong before moving on.
